# Phase 10 B4 — Service-XP Rate Redesign Options Paper

**Status:** OPTIONS ONLY — no rate is implemented by this paper. Any adoption
of an option below is an explicit human numeric authorization (proposal v0.2
§6; BAL-001; HD-TST-01). **Default if declined: the flat [PROVISIONAL] rates
stand, characterized in the B4 section of the balance report.**

Author: Buffy — Codebuff agent (Phase 10 implementation), 2026-09-17.

## 1. Problem shape (characterization, verified)

Every service-XP award in the fork is flat and action-count-driven: repeating
the action repeats the XP, regardless of outcome, magnitude, or target state.
The full site inventory with citations is in the B4 section of
`docs/phase10_balance_report.md` (generated by `cmd/phase10report`). The only
rate-shaped hook today is the merchant sale award (price/100, unique-buyer
full / repeat 25% — `economy.go:297-303`).

The predecessor GDD's progression-time horizons (§33.3: basic mastery 40–60 h,
elite 80–120 h) cannot be projected honestly against flat per-action rates at
fast-cycle testbed cadences — this is why §33.3 rows are NOT-MEASURABLE in the
B3 report. A redesign is a PREREQUISITE for any future honest progression-time
telemetry, but this paper implements nothing.

## 2. Candidate shapes (predecessor GDD §7.2.3; each needs a numeric ask)

For each option: the shape, the hook point, and the explicit numeric asks a
human would have to answer. None has a proposed value.

### Option A — per-point wound healing (medical)

- **Shape:** heal XP scales with wound points actually removed, not the
  action. Site: `services.go:136` (replace flat `services.HealXP=50`).
- **Hook:** the handler already knows `amount` (points healed).
- **Numeric asks:** XP per wound point (or per N points); cap per target per
  day; whether revives keep a separate flat award.

### Option B — per-tick battle-fatigue healing (entertainer)

- **Shape:** performance XP accrues per viewer per BF point actually healed
  per tick, replacing tip-driven-only flow. Site: the perform/watch tick
  (`tickServices`), pool `entertaining`.
- **Numeric asks:** XP per BF point per viewer per tick; idle cap; whether
  tips remain a bonus multiplier and its magnitude.

### Option C — per-application buff scaling (medic)

- **Shape:** buff XP scales with buff magnitude (tier-derived), not flat per
  application. Site: `services.go:190` (replace flat `services.BuffXP=50`).
- **Numeric asks:** XP per magnitude point or per tier step; diminishing
  returns on repeated application to the same target (window length; decay
  curve class — linear/hyperbolic — is itself a decision).

### Option D — diminishing-returns hook (general)

- **Shape:** a shared decay wrapper around `AddCharacterXP` per
  (character, pool, target) triple: repeated identical service to the same
  target within a window decays toward a floor. Mirrors the merchant
  repeat-buyer 25% precedent.
- **Numeric asks:** window length; decay curve class; floor as % of full;
  whether the merchant precedent unifies under it.

## 3. Interaction constraints (verified against current code)

- Skill tier costs (`tierXPCosts = 1000/5000/15000/40000`, `professions.go:160`)
  are LOCKED-adjacent [PROVISIONAL] — any XP-rate change shifts time-to-tier
  and therefore the §33.3 horizons; a rate redesign decision should record the
  intended horizon BEFORE numbers are chosen (the tail wags the dog).
- All award sites are best-effort `_ =` calls; a rate wrapper must preserve
  that failure discipline (telemetry and XP never fail gameplay actions).
- Quota/diminishing-XP machinery from Phase 9 (quota service XP +250 caps)
  already exists for missions — Option D could extend rather than duplicate
  it; reusing it is a structural decision for the human.

## 4. Recommendation (non-binding)

Characterize first (done — B4 report section), defer all numeric asks until a
human names the intended §33.3 horizon. Among the options, Option A is the
smallest honest step (outcome-shaped, single site, no new machinery); Option D
is the most general but touches every site and should follow, not precede, a
horizon decision.
